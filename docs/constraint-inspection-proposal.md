# Constraint Inspection Proposal for TOPC

This document proposes a compiler-inspection feature set that makes the internal constraints of TOPC visible to students and instructors.

The goal is to develop this feature first in `topc`, validate that it is useful for teaching and debugging, and then carry the design into `sopc`.

## Motivation

TOPC already exposes some useful internal state with `--pt`, which prints inferred types at the end of semantic analysis. That is helpful, but it hides the intermediate reasoning that produces those types.

As the language grows, students will benefit from seeing the actual constraints generated by the compiler, including:

1. Type inference constraints.
2. Call-graph / CFA constraints.
3. Ownership and move constraints.
4. Borrow and lifetime / region constraints, if and when those are made explicit.

The teaching value is in showing how the compiler reasons, not just in showing the final result.

## Proposal Summary

Add a family of inspection options centered on a new umbrella flag, tentatively `--pc`, for "print constraints".

Suggested design goals:

1. Make the compiler's reasoning visible at multiple levels.
2. Keep the output stable enough for regression testing.
3. Tie every printed item back to source locations and compiler phases.
4. Preserve `--pt` as the final inferred-type view, rather than overloading it.
5. Make the notation used to communicate constraints a deliberate design choice we are free to define.

## What to Expose

The compiler already has several distinct analysis systems. The proposal is to surface them separately, rather than collapsing everything into one dump.

### 1. Type constraints

These are the equations and relationships that drive inference.

Useful output might include:

1. Fresh type variables introduced for expressions and declarations.
2. Equality and unification constraints.
3. Generalized type schemes for eligible declarations.
4. Instantiated types at call sites.

This is especially important for polymorphic inference, because students need to see the difference between:

1. the generalized scheme stored for a definition, and
2. the instantiated version created at each use site.

### 2. CFA / call-graph constraints

The compiler already constructs control-flow and call-graph information. Exposing that information would help students understand how indirect calls, reachability, and function targets are discovered.

Examples of useful items:

1. Direct call edges.
2. Indirect / conservative call targets.
3. Function reachability summaries.
4. Source-site annotations for each edge.

### 3. Ownership and move constraints

TOPC already reasons about ownership through analysis and code generation. A printable form of this reasoning would help explain:

1. why a binding is considered moved,
2. why a value must be destroyed,
3. why a use-after-move is rejected, and
4. how owned values differ from borrowed values.

### 4. Borrow and lifetime / region constraints

As TOP evolves, the borrow and lifetime story will likely become richer. When that happens, the printed constraints should make it clear which regions or lifetimes must outlive others, and why.

This does not require deciding the final surface notation now. The proposal is to make the debugging interface available first, then refine the exact notation as the analysis matures.

## Suggested CLI Shape

`--pc` should be the umbrella switch, with focused submodes for the different analyses.

One possible direction is:

1. `--pc=type` for type inference constraints.
2. `--pc=cfa` for call-graph / CFA constraints.
3. `--pc=ownership` for move and destruction reasoning.
4. `--pc=borrow` for borrow and lifetime constraints.
5. `--pc=all` for a complete dump.

The exact syntax does not need to be fixed yet. The key idea is that the notation and structure are ours to design, and we should choose something that is both teachable and testable.

## Notation Principle

We are free to design the notation used to communicate constraints to students.

That is an important advantage, because the goal is not to mirror an existing research system exactly. The notation should be:

1. easy to read in class,
2. easy to diff in tests,
3. compact enough to fit in terminal output,
4. precise enough to diagnose real compiler behavior, and
5. consistent across constraint families.

The proposal therefore recommends designing a TOPC-specific notation rather than importing one wholesale from another compiler or paper.

## Output Format Guidelines

To make the feature useful in practice, each printed constraint should include:

1. the compiler subsystem or phase that generated it,
2. the source span or AST node that originated it,
3. a compact human-readable form,
4. enough structure to allow stable golden tests.

An example shape, independent of final notation, might look like:

```text
[type]     test.top:12:5-12:9   α3 = Seq(α4)
[call-graph] test.top:20:1-20:8  call f -> {g, h}
[borrow]   test.top:27:7-27:14   region(r1) outlives region(r2)
[own]      test.top:31:3-31:10   value x is moved here
```

The exact syntax can and should evolve during implementation.

## Generalized vs Instantiated Types

One especially useful teaching mode would be to expose both generalized schemes and call-site instantiations.

This helps students see why a function can have one generalized form in the environment but many concrete instantiations throughout the program.

Recommended behavior:

1. print generalized schemes for eligible definitions,
2. print the instantiated type at each call site,
3. tie the instantiation back to the definition it came from.

That distinction is often where students first encounter polymorphic inference subtleties, so it is worth making explicit.

## Why This Should Be Built in TOPC First

Implementing the constraint views in `topc` first has several benefits:

1. It forces us to define the user-facing notation before SOPC depends on it.
2. It gives us a stable pedagogical interface to refine while the compiler is still simpler.
3. It creates a reusable inspection layer that can carry forward into `sopc`.
4. It makes it easier to decide which analyses should be visible by default and which should remain expert-only.

This is especially valuable because SOPC will add more complex ownership and lifetime behavior, and those features will be much easier to teach if the introspection story is already in place.

## Suggested Development Order

1. Add the basic constraint-printing plumbing in TOPC.
2. Define the initial notation and output format.
3. Make type constraints visible first, since they are the simplest and most familiar.
4. Add CFA and call-graph views.
5. Add ownership and borrow / region views as those analyses mature.
6. Stabilize the output format with tests.
7. Carry the feature set into SOPC after the TOPC version feels solid.

## Success Criteria

This proposal is successful if students can answer questions like:

1. What constraints did the compiler generate for this program?
2. Why did this function get this generalized type?
3. What instantiated type did this call site use?
4. Why did the borrow or ownership analysis reject this code?
5. Which phase introduced the constraint that caused the failure?

If the inspection feature helps answer those questions clearly, it will be worth carrying forward into SOPC.
